Design Note — Idempotent Background Transaction Processing Service

A background console service (Java 17 / Spring Boot CommandLineRunner, no web layer, no DB) that ingests banking CREDIT/DEBIT/REVERSAL requests and applies each one to an in-memory account ledger exactly once, regardless of duplicate replays, out-of-order arrival, or transient failures, via a dedicated background-processing component that decouples ingestion from processing (US-12). This note is the eight required sections of the assessment's design deliverable — Architecture, Idempotency design, Duplicate detection logic, Out-of-order handling strategy, Retry and failure handling, Observability approach, AI-assisted development usage, and Production hardening recommendations — grounded directly in the current transaction-service/ source, the current Cucumber feature files, and DESIGN.md's traceability matrix, not a paraphrase of them. Every claim below names the requirement ID, the class/file that implements it, and the scenario that tests it.

1Architecture

Stack (DD-01): Java 17 + Spring Boot, run as a single CommandLineRunner batch — no web layer and no real database, per the assessment's ground rules. That keeps the build boring and fully testable: every collaborator below is a plain class wired by hand in TransactionServiceApplication, with no framework magic between the pieces that actually matter for idempotency/ordering/retry.

Each pipeline stage is a separate class behind a narrow interface where it needs to be swappable later (US-10 / L2-FR-10 / NFR-07) — TransactionSource and IdempotencyStore are interfaces specifically so the in-memory implementations can be replaced by a real queue and a real datastore without touching TransactionProcessor, which has no import on either concrete class.

A layer not yet in DESIGN.md's User Stories

RequestSchemaValidator and InMemoryTransactionSource's use of it are current working-tree code (git status shows them as newly added, not yet committed). They sit before Validator: a raw JSON record is checked for the right shape (seven required fields, no extras) and sane field formats (no negative/zero/degenerate ids, a real CREDIT/ DEBIT/REVERSAL, a 3-letter currency code, a positive integral sequenceNumber) before it is ever deserialized into a TransactionRequest. A record that fails is logged and excluded — the same "one bad record never stops the batch" principle as AC-02.3, applied one layer earlier, at the wire format rather than the business object.

Background processing component (US-12 / L2-FR-13, DD-12)

Ingestion and processing were originally one inline call stack — CommandLineRunner looped over the batch and called processor.process(request) directly, on the same thread. That satisfied every other User Story but left no actual architectural separation between "ingestion" and "a background processing component" — two distinct items on the assessment's own checklist. The fix, BackgroundWorker, is a producer/consumer split: the ingesting thread submit()s every request to a BlockingQueue and returns immediately (AC-12.1/AC-12.2); a single dedicated consumer thread (a 1-thread ExecutorService) drains the queue and calls TransactionProcessor.process for each one. 

public void submit(TransactionRequest request) {   // producer side — never blocks
    submittedCount.incrementAndGet();
    queue.add(request);
}
private void drainLoop() {                          // single consumer thread
    while (true) {
        TransactionRequest request = queue.take();   // blocks until something is enqueued
        try { processor.process(request); }
        finally { synchronized (drainLock) { processedCount.incrementAndGet(); drainLock.notifyAll(); } }
    }
}
public void awaitDrained() {                         // producer waits once, at the end
    synchronized (drainLock) {
        while (processedCount.get() < submittedCount.get()) { drainLock.wait(); }
    }
}

transaction-service/src/main/java/.../worker/BackgroundWorker.java, wired in TransactionServiceApplication

Deliberately one consumer, not a pool (AC-12.3): DD-02's out-of-order logic depends on exactly one global cursor (SequenceBuffer.lastResolvedSequence) advanced in strict arrival order, and the idempotency store is a check-then-set, not an atomic claim (already a named gap in §8). A pool of concurrent consumers would race on both, silently breaking NFR-01 and NFR-02 to gain throughput — so this stays single-threaded until both of those are fixed first (see Production hardening, §8). awaitDrained() is also what closes a race an inline loop never had: without it, the processing summary could be computed before the worker has actually finished draining the queue.

Test status: US-12_background_worker.feature exists under transaction-service/src/test/resources/features/ and AC-12.1/AC-12.2/AC-12.3 are all Covered — verified with a real mvn test -Dcucumber.filter.tags="@US-12" run: 3 Scenarios, 18 Steps, all passed. The queue and worker now appear as their own stage between SRC and VAL in the HLD-01 diagram above.

2Idempotency design

NFR-01 / US-04: the same business transaction must take effect on the ledger exactly once, no matter how many times it is submitted, replayed, or retried. The design makes this an explicit, dual-key check rather than relying on a side effect of some other mechanism to catch it incidentally.

Dual-key store (DD-03)

IdempotencyStore tracks two independent keys, checked in this order before any side effect can occur:

  1. requestId — catches a literal retry of the exact same physical attempt (AC-04.1, AC-04.3).
  2. transactionId — catches a different requestId that references the same underlying business transaction (AC-04.2).

This was a deliberate correction, not the original design: the first pass checked only requestId and depended on the sequence-staleness check (FC-03) to incidentally catch a reused transactionId under a new requestId. That is fragile — a duplicate reusing a fresh, never-before-seen sequence number would slip through undetected. It was caught by deliberately cross-checking this design against an independent AI session's analysis of the same assessment (see §7 below), which argued transactionId is the more direct dedup key for exactly this case — and was right. 

public interface IdempotencyStore {
    boolean isProcessed(String requestId);
    void markProcessed(String requestId);
    boolean isTransactionProcessed(String transactionId);
    void markTransactionProcessed(String transactionId);
}

transaction-service/src/main/java/.../store/IdempotencyStore.java, InMemoryIdempotencyStore.java (java.util.concurrent.ConcurrentHashMap-backed sets)

Where the side effect is actually guarded

The only side effect idempotency protects is AccountLedger.apply(). The store is checked before that call and written to only after it succeeds (TransactionProcessor.attemptProcess): 

ledger.apply(accountId, type, amount);          // the side effect
sequenceBuffer.markResolved(request);
idempotencyStore.markProcessed(requestId);       // <- key #1 written
idempotencyStore.markTransactionProcessed(txId); // <- key #2 written
setStatus(request, PROCESSED);

Note on ordering: the ledger write happens before the idempotency keys are marked. Today that gap is harmless — the engine is single-threaded and synchronous, so nothing can resubmit the same requestId between those two lines. It stops being harmless the moment retries move to a separate process or queue consumer (see Production hardening, §8) — a crash in that gap would let a redelivered message re-apply to the ledger. Flagged here rather than silently fixed, since fixing it properly needs the atomic claim-then-apply pattern, not just reordering two lines.

3Duplicate detection logic

Three independent checks run, in this fixed order, before a request is allowed anywhere near the ledger (TransactionProcessor.process). All three mark the request DUPLICATE with zero ledger side effect; none of them halt the rest of the batch.

#CheckCatchesCode
1idempotencyStore.isProcessed(requestId)Exact same physical request replayed (AC-04.1)TransactionProcessor.process, line ~59
2idempotencyStore.isTransactionProcessed(transactionId)A different requestId for the same business transaction, even arriving later (AC-04.2)TransactionProcessor.process, line ~65
3sequenceBuffer.isAlreadyResolved(request)A brand-new requestId/transactionId whose sequenceNumber is at or before the batch's resolved cursor — a stale replay by position, not by identifier (AC-04.4)SequenceBuffer.isAlreadyResolved + TransactionProcessor.process, line ~71

Check 3 exists because checks 1 and 2 are both identifier-based; nothing stops a genuinely new transaction/request pair from being submitted "again" at a sequence slot the batch has already moved past. Found during the manual code-level coverage review (DD-11) — it is a real, independent dedup path with its own scenario, not a restatement of checks 1/2.

4Out-of-order handling strategy

US-05 / L2-FR-07 / NFR-02: §9.5 of the problem statement offers three explicit options and asks the candidate to justify the choice, not just implement one. Option A — sequence-based buffering — was chosen, with a single cursor for the whole batch, not per account (DD-02). A request is released for processing only once every earlier sequence number has been resolved, whether that resolution was a success or a definitive failure.

Why Option A, and not B or C (DD-02)

OptionMechanism (as specified)Why it was/wasn't chosen
A — Sequence-based
Chosen		 Each request carries a sequenceNumber; future numbers are held pending; a request processes once every prior required number has arrived; missing numbers are reported. sequenceNumber is a field the §9.8 sample data already carries, with documented expected behavior keyed on it (seq=2 held pending until seq=1 arrives, then released) — the test data was built assuming exactly this mechanism. It gives a deterministic, example-testable final state (AC-05.1–AC-05.3), and composes for free with the dual-key idempotency design (DD-03): "sequence at or before the resolved cursor" doubles as a third duplicate-detection signal (AC-04.4), with no extra mechanism needed.
B — State-based Each transaction has a valid state-transition model; an event processes only if the transition is valid; invalid/premature transitions are marked pending or rejected. Rejected. This fits one entity's own lifecycle (e.g. ORDER_CREATED → SHIPPED → DELIVERED), where "order" is derived from which transition is legal next. US-05's real requirement is cross-transaction ordering for the same account (seq=1 must resolve before seq=2 can touch that account's balance) — a transition table has no native way to express "wait for a different transaction's slot" without also attaching a sequence/position, at which point it collapses back into Option A anyway. This design already has a genuine state-transition model (US-03 / TransactionStatus), but it answers a different question — "what happened to this one request" — not "whose turn is it"; conflating the two would blur both.
C — Deterministic latest-state Uses eventTime/version to determine the latest valid state; older duplicates or stale updates are ignored ("latest wins"). Rejected. This is a replace-on-newer-wins policy — correct for a domain where an entity has one current value and a stale update should be discarded (e.g. "latest known address"), not for this domain: every CREDIT/DEBIT/REVERSAL is its own side effect that must be applied exactly once, not a competing write to one mutable field. Silently "ignoring" an older transaction because a newer one arrived first would drop a real movement of money — the opposite of what idempotency is meant to protect. The §9.8 sample data also carries no eventTime/version field at all, only sequenceNumber — Option C would need data the spec and the sample batch never provide.

Within Option A — why one cursor, not per-account (DD-02)

The first draft used a per-account cursor. Running the engine against the real §9.8 sample data broke it: ACC-203 appears exactly once, at sequenceNumber=5, with no sequence 1–4 ever existing for that account. Under a per-account cursor, that request could never become "ready" — it would wait forever and never reach the retry logic, contradicting the spec's own documented expected outcome for that row. A single batch-wide cursor, advanced on every resolved sequence number (including validation failures, so one permanently-failed record never blocks everything after it), reproduces all six §9.8 expected outcomes exactly. This was found empirically, not by inspection, and is recorded as a genuine design correction, not a stylistic choice. 

public synchronized boolean isReadyToProcess(TransactionRequest request) {
    return request.getSequenceNumber() == lastResolvedSequence + 1;
}
public synchronized boolean isAlreadyResolved(TransactionRequest request) {
    return request.getSequenceNumber() <= lastResolvedSequence;
}
public synchronized void markResolved(TransactionRequest request) {
    lastResolvedSequence = Math.max(lastResolvedSequence, request.getSequenceNumber());
}
public synchronized TransactionRequest pollReady() {
    return buffered.remove(lastResolvedSequence + 1); // cascades: caller loops until null
}

transaction-service/src/main/java/.../ordering/SequenceBuffer.java

A request whose sequence is ahead of the cursor is parked in a ConcurrentHashMap<Long, TransactionRequest> keyed by sequence number and marked PENDING_ORDER. Every time any request resolves, the processor loops pollReady() until it returns null, so a single arrival can cascade-release several buffered requests in one pass (AC-05.2, reinforced by the cascade-release scenario added in DD-11 covering 2+ hops, not just one).

5Retry and failure handling

US-06 / L2-FR-08, L2-FR-09 / NFR-03: a transient failure is simulated via request.getSimulatedFailures() — while the current retryCount is below that threshold, attemptProcess throws TransientProcessingException instead of calling the ledger. RetryPolicy (DD-04) bounds retries at a configurable max, 3 by default, externalized as a constructor argument rather than hardcoded in the processor. 

private void attemptProcess(TransactionRequest request) {
    setStatus(request, PROCESSING);
    try {
        if (request.getRetryCount() < request.getSimulatedFailures()) {
            throw new TransientProcessingException("simulated transient failure");
        }
        ledger.apply(accountId, type, amount);
        sequenceBuffer.markResolved(request);
        idempotencyStore.markProcessed(requestId);
        idempotencyStore.markTransactionProcessed(txId);
        setStatus(request, PROCESSED);
    } catch (TransientProcessingException e) {
        if (retryPolicy.shouldRetry(request)) {
            request.incrementRetryCount();
            setStatus(request, RETRY_PENDING);
            attemptProcess(request);              // retried inline, same call stack
        } else {
            sequenceBuffer.markResolved(request);
            setStatus(request, FAILED);
            request.setFailureReason("retries exhausted after " + request.getRetryCount() + " attempt(s): " + e.getMessage());
        }
    }
}

transaction-service/src/main/java/.../service/TransactionProcessor.java (attemptProcess), retry/RetryPolicy.java

Because IdempotencyStore is only written to on the success branch, a transaction that fails on attempts 1–3 and succeeds on attempt 4 is marked PROCESSED exactly once (AC-06.3) — the earlier failed attempts never touched the store or the ledger, so there is nothing for idempotency to clean up after.

Implementation note, not a defect: retries here are synchronous and immediate — recursion within the same call, bounded by maxRetries, with no backoff/delay. That is fine for a deterministic, in-memory simulation driving a fixed sample batch; it is explicitly named in Production hardening (§8) as something a real deployment must externalize to scheduler/queue redelivery with backoff.

Masking (US-09 / NFR-06, DD-10)

public static String mask(String accountId) {
    if (accountId == null || accountId.length() <= 4) return "***";
    return "***" + accountId.substring(accountId.length() - 3);
}

util/AccountIdMasking.java — the one place that decides "masked", shared by TransactionProcessor and AccountLedger so they can't drift apart on what masking means.

AccountLedger's own debug line was brought in line with this too (DD-10): it used to print the raw amount and resulting balance. AC-09.1 names only account numbers/PII, so that wasn't a literal violation, but no other class in the codebase logs amount/balance, so it was fixed for consistency rather than because the AC strictly required it.

Run summary (AC-08.1 / L2-FR-11, DD-08)

Computed once over the whole batch by terminal status only (so a mid-retry RETRY_PENDING never pollutes the count), and — since DD-08 — actually logged via SLF4J rather than a bare System.out.println that bypassed Logback entirely: 

public static ProcessingSummary of(List<TransactionRequest> requests) {
    ProcessingSummary summary = new ProcessingSummary();
    requests.forEach(r -> summary.countsByStatus.merge(r.getStatus(), 1, Integer::sum));
    log.info(summary.report());   // "SUMMARY: PROCESSED=.. DUPLICATE=.. FAILED=.. ..."
    return summary;
}

7AI-assisted development usage

Built with Claude Code, iteratively, in BDD/ATDD order — User Stories and Acceptance Criteria first, then HLD/LLD/flowcharts, then Cucumber feature files (one scenario per AC), then the engine classes and step definitions. Three reference open-source "idempotent payment" repos were pulled and read for comparison before committing to this design; all three covered idempotency well but none handled out-of-order/sequence processing — confirming that was the differentiating, harder half of the assessment.

Every piece of generated code was run and verified against the real §9.8 sample data, not trusted by inspection. Doing so surfaced four real defects, including the genuine design correction in DD-02 (per-account → batch-wide cursor).

Independent second opinion

A second, independent AI session's own analysis of the same assessment was deliberately cross-checked against this design — used as a second opinion, not to generate code. It agreed on the domain, the three failure modes, and Option A ordering. It disagreed on the dedup key, arguing for transactionId where this design had used requestId alone — and was right (adopted as DD-03). Its other gap analysis (stuck-pending TTL, atomic-claim concurrency, permutation testing, key retention) was judged correct but out of scope to fix in the time available, and is carried into Production hardening (§8) below rather than silently dropped.

8Production hardening recommendations

These are explained, not built — explicitly out of scope for this assessment's console-batch form factor (DD-01), but named rather than silently dropped (per §9.7's ask to identify trade-offs and next steps).

Infrastructure swaps (DD-05)

Durable stores. Swap the in-memory IdempotencyStore and ledger for Redis/a DB, with a unique constraint on requestId — not a check-then-set in application code.
Real queue. Swap TransactionSource for Kafka/SQS with consumer-group ordering, replacing the in-memory batch read.
Per-account concurrency control. Add optimistic concurrency or distributed locking for NFR-04 once the ledger is no longer a single in-process map.
Real metrics/tracing. Add Micrometer metrics and distributed tracing beyond console/log-file observability.
Payload fingerprinting. Add a content fingerprint alongside requestId to catch a key being reused for a genuinely different transaction (today the id alone is trusted).
Scheduler-driven retries with backoff. Replace the synchronous inline retry in attemptProcess (§5) with scheduler/queue redelivery and exponential backoff, and make the ledger-write / idempotency-mark ordering noted in §2 atomic across process restarts.

Named open gaps (not fixed — tracked deliberately)

Concurrent-duplicate race. US-07's concurrency test proves the ledger serializes per-account updates; it does not prove the idempotency check itself is race-free under two truly simultaneous first attempts for the same key. Safe today only because the engine is single-threaded — a real concurrent system needs an atomic claim (e.g. INSERT ... ON CONFLICT) at the store layer.
No idempotency key retention/TTL. Both key sets grow forever in memory. Production needs a retention window (≥ the longest client retry window) and a backing store, not an unbounded in-memory set.
Permutation/invariant testing would be stronger than fixed expected values. Current tests assert specific outcomes for the §9.8 batch's given order. A stronger oracle shuffles the batch and asserts the final ledger state is invariant regardless of arrival order — property-based, not example-based.
AC-11.2 (mutation-style regression test) is a self-imposed stretch AC, still not automated. L2-FR-12's literal text only asks for tests covering duplicate/out-of-order/invalid/retry scenarios — fully satisfied by AC-11.1 and the US-02/US-04/US-05/US-06 scenarios it packages (all passing; L2-FR-12 itself is fully covered). AC-11.2 is an additional criterion layered on top of that, asking the suite to demonstrate it would fail if the idempotency check were broken — a mutation-testing-style check needing a tool like PIT or a deliberately-broken build variant, neither of which fits this repo's one-feature-per-AC pattern. Reviewed with the user, left as a named, honestly-unautomated stretch item rather than force-fit.
TransactionType.REVERSAL is DEBIT-identical (DD-11). AccountLedger.apply() always subtracts for REVERSAL, which is only correct for reversing a CREDIT — reversing a DEBIT would double-subtract instead of crediting back. No AC or scenario exercises REVERSAL at all, so no test has ever caught this.
No overdraft/insufficient-funds rule. DEBIT and REVERSAL subtract unconditionally; nothing prevents a balance from going negative, and no AC specifies a minimum-balance rule.
Background worker queue is in-memory and unbounded (DD-12). BackgroundWorker's BlockingQueue has no bound, no persistence, and no backpressure — a producer that outruns the single consumer grows the queue in memory forever, and a crash loses whatever is still queued. Production needs a durable broker (Kafka/SQS) and a bounded queue with backpressure and dead-letter handling.
Scaling the worker beyond one consumer is a named, undone follow-on (DD-12). AC-12.3 deliberately pins a single consumer because DD-02's global cursor and the idempotency check-then-set above both assume one thread. A worker pool needs two changes together — an atomic idempotency claim and per-account queue partitioning — not implemented here.
Ordering-scope ambiguity and stuck-pending TTL — carried forward from §4, both still open.
