## 2. Git branches

This repo currently has two branches:

### `main` — the final source

**`main` is the final, current, deliverable state of the code.** Every
file referenced in section 1 above, as it exists on `main` right now, is
what's being delivered. If you only check out one branch, check out `main`.

It reflects, in order:
- The original 9-iteration build (US-01 through US-11, one feature +
  engine class at a time)
- DD-07–DD-10: closing tooling gaps found by auditing the test-evidence
  artifacts themselves (persisted logs, machine-readable `cucumber.json`,
  PII masking) against DESIGN.md
- DD-11: a manual, code-level test-coverage gap review (reading the actual
  engine logic against every Acceptance Criterion, not just checking that a
  Cucumber tag existed) — which added/widened several scenarios and fixed
  two vacuous test assertions
- A full reformat of the test data's id conventions, and the addition of a
  production-side JSON schema validator (`schema/RequestSchemaValidator`)
- Everything verified green: `36 Scenarios (36 passed)`, `142 Steps (142 passed)`

### `design-baseline` — the pre-gap-review snapshot

**`design-baseline` is a frozen point-in-time snapshot**, not an
alternative or competing version of the code. It was branched from `main`
at the commit immediately after DD-10 (the observability/PII-masking
fixes) and immediately before the DD-11 gap-review implementation work
began — i.e. it captures "design + all prior fixes complete, but the
manually-found coverage gaps not yet closed."

Its purpose is purely **before/after comparison**: if you want to see
exactly what the manual gap-review pass (DD-11) changed — which
Acceptance Criteria gained coverage, which test assertions were fixed,
which test-data files were reformatted — diff it against `main`:

```bash
git diff design-baseline main -- DESIGN.md
git diff design-baseline main --stat
```

`design-baseline` is **not** meant to be built, run, or tested on its own;
it predates test-data reformatting and the schema validator, so running
`mvn test` against it will not reflect the final, delivered behavior.
Build and test against `main`.
